# Update, deprecation, and rollback procedure

1. Inventory current pins before changing anything: `examples/ruby-rails/Gemfile`, `examples/ruby-rails/Gemfile.lock`, `examples/ruby-rails/Dockerfile`, `.github/workflows/ci.yml` (`ruby-rails` job), `sdk/typescript/playwright.ruby-rails.config.mjs`, and `examples/ruby-rails/.env.example`. Record versions only (Ruby/Bundler/Rails/Puma/Redis client/JSON/Caddy/Cormier.Realtime SDK-protocol-gateway), never live environment values.
2. Review upstream release notes/advisories/support windows and compatibility. Keep the Rails/JSON compatibility guard: validate request parsing behavior before adopting a new major `json` line (the current project intentionally pins `json` `2.21.2`).
3. Preserve mutable deployment configuration and data outside source control. Keep every domain/origin/host/port/Redis prefix/Secret runtime-configurable, and never place credentials in `Dockerfile`, `UPDATE.md`, committed `.env` files, build logs, or command history.
4. Apply dependency/runtime updates surgically. Prefer targeted lock updates (for example `bundle _4.0.20_ lock --update <gem>`) over broad graph churn, then review the full `examples/ruby-rails/Gemfile.lock` diff. Rebuild canonical browser assets from `sdk/typescript` and keep `examples/shared-web/dist` and `sdk/typescript/dist` as the only asset sources (do not copy vendored gems or generated artifacts into `examples/ruby-rails`).
5. Validate with the same checks the repository runs today:
   - Locked Ruby adapter checks in `examples/ruby-rails`: `bundle _4.0.20_ check`, `bundle _4.0.20_ exec rubocop`, `bundle _4.0.20_ exec ruby test/reference_config_test.rb`, `bundle _4.0.20_ exec brakeman --no-pager --quiet`, and `bundle _4.0.20_ exec bundle-audit check --update`.
   - Build the container from repository root with `docker build --file examples/ruby-rails/Dockerfile --tag cormier-ruby-rails:<tag> .`, confirm non-root runtime (`USER 65532:65532`), and run a HIGH/CRITICAL image scan.
   - Run shared browser smoke scenarios with `npx playwright test --config playwright.ruby-rails.config.mjs`, including login, ticket, connect/subscribe/publish/receive, reconnect, logout, expiry, rejected-origin, gateway/Redis outage, redaction, health, second-run, and clean shutdown behavior.
6. Deploy progressively and monitor health plus structured lifecycle/error events. Roll back image and configuration together on failure, and restore Redis data only through the approved recovery runbook.

For a release check from the previous supported example version, build both Git revisions with recorded pins, run the same external configuration and canonical browser suite against each image, update without changing Redis prefixes, then roll back and repeat login, ticket, connect, publish/receive, reconnect, logout, and health. The initial 0.1.0 example has no earlier in-repository version, so this two-revision check begins with its first update.

Announce every route, environment key, dependency/runtime line, asset/protocol version, or example deprecation in README and CHANGELOG before removal. Name its replacement, migration and verification steps, rollback, and approved removal release or support window; test old and replacement paths throughout that window. The current release has no deprecations.
