# Cross-platform bootstrap and topology guide

Cormier.Realtime has one versioned bootstrap contract and two supported entry points: `scripts/realtime-bootstrap.sh` for Bash 5 or later and `scripts/Realtime-Bootstrap.ps1` for PowerShell 7 or later. Both call the same Node.js 22+ engine, consume the same JSON configuration, render byte-identical plans and Helm values, use the same bounded operations, and return `0` for success, `1` for a prerequisite/execution failure, `2` for invalid input, or `3` for a safety stop.

Use `scripts/realtime-redis-secret.sh` or `scripts/Set-RealtimeRedisSecret.ps1` before a managed-Redis install. Those wrappers share one implementation, accept explicit context/namespace/Secret/key/password-file parameters, remove trailing CR/LF bytes, reject embedded newlines and identical credentials, and submit Secret data through standard input without exposing password values in process arguments. Run either bootstrap wrapper with `help`/`-Action help` for its shared command summary and use each PowerShell script's `Get-Help -Full` output for parameter help.

## Quick start

Copy `bootstrap/config.example.json` for non-HA or `bootstrap/config.ha.example.json` for HA to ignored `.bootstrap/env/<environment>/config.json`, replace every example target with the intended environment, and keep the selected `topology` aligned with the file. Never put credentials in the file. It contains only existing Kubernetes Secret names and configurable key names. For a public registry image, leave `image.pullSecretName` empty; for a private image, create the pull Secret out of band and reference only its name.

```bash
export CORMIER_BOOTSTRAP_CONFIG=/secure/config/realtime-dev.json
bash ./scripts/realtime-bootstrap.sh plan --profile non-ha
bash ./scripts/realtime-bootstrap.sh prerequisites --profile non-ha
bash ./scripts/realtime-bootstrap.sh install --profile non-ha --name-suffix team-a
```

```powershell
$env:CORMIER_BOOTSTRAP_CONFIG = 'C:\secure\config\realtime-dev.json'
./scripts/Realtime-Bootstrap.ps1 -Action plan -Profile non-ha
./scripts/Realtime-Bootstrap.ps1 -Action prerequisites -Profile non-ha
./scripts/Realtime-Bootstrap.ps1 -Action install -Profile non-ha -NameSuffix team-a
```

`--config`/`-Config` takes precedence over `CORMIER_BOOTSTRAP_CONFIG`. `--name-suffix`/`-NameSuffix` overrides the configured suffix, derives the release and Redis instance identities together, and writes the ignored `.bootstrap/naming.json` manifest consumed by other automation. The lifecycle actions are `prerequisites`, `plan`, `bootstrap`, `backup`, `install`, `update`, `validate`, `rollback`, `recover`, and `teardown`. `bootstrap` performs locked .NET restore and a Release build; `backup` captures the current target without changing it. `organize --dry-run` previews deterministic moves from a legacy flat `.bootstrap` directory without writing a manifest or lifecycle log, `organize` applies them and writes a manifest under `.bootstrap/organization`, and `restore-layout --manifest <file> --dry-run` previews the reverse operation before `restore-layout --manifest <file>` applies it. Bash flags use kebab case; PowerShell parameters use normal PowerShell casing. `--dry-run`/`-DryRun`, the timeout, topology confirmation, backup path, manifest path, and force switch have identical meaning.

## Topology decision

`non-ha` uses one gateway, standalone managed Redis when selected, no autoscaler, no gateway or Redis disruption budget, and no spread constraint. It is intended for development or explicitly cost-constrained environments. A pod, node, Redis, ingress, storage, maintenance, or rollout interruption causes downtime; persistence is not failover and Redis Pub/Sub events cannot be replayed.

`ha` requires at least three configured and schedulable failure domains. Ready nodes with `NoSchedule` or `NoExecute` taints are excluded because the generated gateway has no tolerations. It uses three gateway replicas, a two-available disruption budget, zone/host spreading, a rolling update with zero unavailable replicas, autoscaling from three replicas, and either managed Redis replication plus Sentinel or an operator-approved external HA endpoint. Managed Redis nodes use a hard zone spread so Redis and Sentinel quorum cannot collapse into one failure domain. Cluster capacity, managed-Redis storage, DNS/TLS, ingress, MetalLB, and observability remain environment inputs and must be validated for the target.

The profile is explicit in configuration and is passed into the application as `Gateway__Topology`; replica count never selects it implicitly. Both the WebSocket route and HTTP fallback base path are configuration inputs. The generated Traefik route sends them to the same Service and enables secure cookie affinity required by multi-request HTTP fallback connections.

## Plans, updates, and recovery

Every invocation validates the complete configuration before contacting a cluster, expands only the literal `{environment}` token from the validated `environment.name`, and writes a secret-redacted, stable-key-order plan and rendered values beneath ignored `.bootstrap/env/<environment>/lifecycle`. Paths are rechecked after expansion and cannot escape the repository. The reviewed plan and SHA-256 cover both gateway values and every generated managed-Redis override, including storage class and size. Configure the ingress origins and both transport paths, Kubernetes-syntax Traefik pod labels, explicit direct-client namespace/pod selectors for ingress-free mode, exact trusted proxy CIDRs, optional immutable gateway image digest and existing image-pull Secret, managed Redis OCI chart repository/version/archive checksum and immutable component image coordinates, the legacy repository used during first-update adoption, external Redis TLS and egress CIDRs, DNS-label observability cluster identity, monitoring namespace/pod selectors, and any OTLP egress CIDRs or workload selectors explicitly. The WebSocket route is compared case-insensitively with the fallback route and the gateway's fixed ticket, health, and metrics endpoints before a plan is accepted. The Redis `credentialKey` is also the managed ACL username, and managed mode requires a distinct `adminCredentialKey`, preserving separation between the restricted ACL user and administrator. Secret names accept Kubernetes DNS-subdomain syntax. Origins must not contain URL userinfo; OTLP endpoints must contain neither userinfo nor query/fragment credentials, and their effective port must appear in `otlpEgressPorts`. Empty OTLP workload selectors remain absent so CIDR-only policies do not widen access. Authenticated OTLP endpoints use the configured existing headers Secret and key. Set `ingress.certificateName` to the cert-manager `Certificate` resource name to enable certificate alerts; leave it empty for an externally managed TLS Secret. Ingress-free plans suppress certificate and edge alerts and do not require Traefik or MetalLB cluster resources. JSON-line logs use `.bootstrap/env/<environment>/logs` in the examples; validated matching logs older than seven days move to its `Archive` directory. Review `plan.json`, `values.json`, `redis-values.json` when managed Redis is selected, the target context/namespace, availability guarantees, change classification, and SHA-256 before mutation.

Legacy organization recognizes only anchored environment slots and accepts every environment name allowed by the configuration contract, including names such as `qa` and `staging`; Windows device names such as `con`, `aux`, `com1`, and `lpt1` are rejected so paths remain cross-platform. Dot-form `config`, `bootstrap`, `install`, `plan`, `update`, and `validate` files use the environment immediately after the first dot; rendered `gateway-<env>` and `redis-<env>` files use the terminal environment token. Consequently, `update.test.dev-alias.log` belongs to test. Directories, `naming.json`, unknown names, and ambiguous names remain at the root. Apply fails before moving anything when a destination already exists, even when the contents match; this avoids silently deleting the source. Symlinked bootstrap roots and destination ancestors are rejected before mutation. Repeating a successful organization is a no-op. Organization and restoration share one workspace lock, and each rename is journaled before it begins so restore can reconcile an interruption between the rename and the next manifest write. A restored manifest cannot be reused. Restore validates every recorded source and destination before moving any file back and never removes the environment directories. Rollback accepts both the configured environment-scoped backup root and the matching legacy `.backups/bootstrap/<release>` root so existing recovery snapshots remain usable during migration.

Every action that writes target artifacts uses the same exclusive target lock; a second global lock is held for the invocation that owns `.bootstrap/naming.json`, preventing cross-target manifest races. Before managed Redis is rendered or changed, the engine obtains the exact chart archive, verifies its configured SHA-256, unpacks it below the ignored target directory, and applies a fail-closed patch that publishes the normal Sentinel Service's not-ready endpoints. The verified archive and provenance metadata remain in that ignored directory, so later backup, update, validation, and recovery reuse local verified bytes instead of depending on the OCI registry. During environment-layout adoption, backup and pre-change capture also search the former `.bootstrap/lifecycle/<release>/charts` cache before declaring provenance unavailable. Preserve that lifecycle cache with the deployment administration workspace: if provenance for the installed chart is unavailable, backup and pre-change capture fail closed rather than downloading current bytes for a mutable repository/version and treating them as trusted. Chart download and extraction share the lifecycle deadline; a timed-out child is terminated and the engine waits for it to close before releasing the target lock. HA values use `OrderedReady`, bounded DNS retries, a 60-attempt Redis startup budget, and a Sentinel startup probe that reapplies the reviewed 10-second TILT trigger after every container start; immutable component digests prevent rolling tags from silently selecting an incompatible Redis data format. The gateway authenticates to Sentinel as its fixed `default` administrator while using the restricted ACL user for data traffic. Configured managed-image pull Secrets are validated and rendered through the upstream chart's global pull-secret setting. Cluster actions use bounded Helm/Kubernetes waits, atomic Helm upgrades, unbounded retained Helm revision history, pre-change release-value backups beneath ignored `.backups/bootstrap/<environment>`, and post-rollout health verification. Target inventory is explicitly filtered to both release names instead of relying on Helm's default list limit. Every cluster-bound Helm and kubectl command carries the configured context explicitly. Update restarts gateway pods after referenced Secret rotation. Recover first rolls and waits for the topology-appropriate managed Redis StatefulSet, then restarts and verifies the gateway, so password rotation cannot leave Redis using stale Secret bytes. Lock ownership is recorded locally; dead same-host owners and cross-host locks older than two hours are atomically claimed for recovery, and only the recorded owner may release a lock, while active or recent owners fail closed. Standalone backup uses only target, API, and release-inventory cluster preflight so degraded desired-state dependencies do not block emergency capture, but it still requires the locally verified provenance needed for a restorable managed-Redis snapshot. Backups fail closed and remove the partial snapshot if Helm returns a plausible inline string, numeric scalar, or scalar-array password, token, secret, credential, private key, authorization value, or cookie; only known Secret-reference fields and non-secret boolean token controls are exempt. A managed Redis backup includes the installed OCI repository, version, exact chart archive, and computed archive checksum; rollback verifies that saved archive instead of substituting the current configured version. An explicitly selected self-contained rollback may proceed when the current release predates the local chart cache, with a warning that its automatic pre-change snapshot lacks a restorable chart archive. A legacy backup without a checksum is accepted only when its repository and version exactly match the current trusted pin. Repeating install/update is supported. The lifecycle references existing Kubernetes Secrets; the configuration-driven password-file helper rejects trailing-line-ending ambiguity, embedded newlines, NUL bytes, all-whitespace values, duplicate keys, and identical credentials before provisioning.

For cluster-changing actions, the installed gateway release is the authoritative source of the prior topology; ignored local state is only an offline planning aid. An installed profile that differs from the requested profile classifies the operation as `topology-conversion`, including on a fresh checkout. Rollback compares the installed topology with the topology stored in the selected backup; its plan, dry run, prerequisite references, and state hash use the exact captured gateway and managed-Redis values. Historical rollback values are not linted against the current working-tree chart because Helm restores the captured revision and its schema. Run `update --dry-run` or `rollback --dry-run --backup <directory>` against the intended cluster, review capacity and downtime implications, then rerun with `--confirm-topology-change` or `-ConfirmTopologyChange`. Storage is never deleted or silently resized. Use `rollback --backup <reported-directory>` (or `-Backup`) to restore the captured gateway Helm revision and managed-Redis values with the captured chart repository/version; releases absent from the snapshot are uninstalled with history retained. Direct managed/external Redis mode conversion, including through rollback, is rejected and requires an explicit operator-managed data migration. `recover` reapplies desired state and verifies rollout health.

`teardown` requires `--force`/`-Force`, refuses production configurations, and removes only the configured gateway and managed-Redis releases. Its preflight checks target identity, API reachability, deletion permission, and release inventory without requiring install-only storage, ingress, observability, capacity, or credential dependencies that may already be unavailable. A successful teardown removes the local current-state marker so later offline plans do not infer a removed topology. Namespace and persistent-volume deletion are deliberately outside this command.

## Validation and failure exercises

Run `validate` before and after changes. CI validates schema failures, secret rejection, deterministic output, cross-shell plan/error parity, both profiles, Helm lint/render, syntax, static analysis, and the repository’s locked restore/test/AOT/security gates.

For an HA release, execute the approved nonproduction failure scenarios in `docs/runbooks/README.md`: gateway pod deletion, node drain with N+1 capacity, Redis failover/recovery, ingress/Traefik interruption, rollout, and planned maintenance. Preserve redacted evidence and confirm readiness, drain behavior, reconnect through another replica, Redis recovery, and restored replica distribution. These disruptive exercises require the runbook’s nonproduction labels and are never run automatically against an arbitrary cluster.

## Support, migration, and deprecation

The former `Bootstrap-Realtime.ps1` and `Deploy-Realtime.ps1` remain compatibility entry points during the v1 transition. New automation should use this cross-shell contract. Their bootstrap, validate/plan, deploy, rollback, remove, backup/recovery capabilities map respectively to `prerequisites`/`install`, `validate`/`plan`, `install`/`update`, `rollback`, `teardown`, and the automatic backup plus `recover` actions. No new feature is added to only one legacy script.

Schema version 2 rejects unknown fields and invalid combinations. Migrate a version 1 configuration by setting `schemaVersion` to `2`, adding `ingress.webSocketPath` and `ingress.httpFallbackPath`, and adding `redis.managedChartArchiveSha256` plus the digest-pinned `redis.managedImages` object from the example. Version 1 configs are intentionally rejected because silently retaining rolling Redis images or an unpatched Sentinel Service recreates the startup and data-compatibility failures this contract fixes. A future incompatible field change increments `schemaVersion` and ships migration notes. Configuration, generated plans, backups, and logs may contain environment identity and must follow the operator’s retention policy; credentials must remain in the configured Secret provider.

Troubleshooting starts with the JSON error path emitted before mutation. A context mismatch, insufficient permissions/capacity, absent storage class/Secret, chart checksum/patch mismatch, missing installed-chart provenance, failed Helm lint, timeout, or unhealthy rollout terminates with a non-zero result while preserving or removing the partial backup as appropriate. Correct the target or prerequisite, run `plan`, then use `recover` or `rollback` as appropriate. The [managed Redis HA runbook](runbooks/managed-redis-ha.md) covers missing Secrets, Sentinel authentication/discovery/TILT, exit 137, incompatible RDB/AOF formats, newline or whitespace `WRONGPASS`, cert-manager readiness, expected unauthenticated HTTP/WSS responses, and abandoned Helm operations.
